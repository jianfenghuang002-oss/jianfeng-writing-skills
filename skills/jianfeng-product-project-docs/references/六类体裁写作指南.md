# 六类体裁写作指南

本文件是 `SKILL.md` 的按需参考。以下结构是可选的论证路径，不是固定模板。每篇文档都应依据实际材料调整。

## 1. 产品需求文档（PRD）

**读者任务**：产品、业务、设计、研发、测试和运营需要决定做什么、为何做、边界是什么，以及如何判断完成。

**需要材料**：用户/角色、真实场景、当前问题与证据、目标、业务规则、权限、现有系统边界、数据定义、依赖方、优先级、验收责任人。缺少关键业务决定时标为待决，不以产品作者偏好代替决策。

**组织方式**：从问题和影响切入，说明目标与成功定义；再交代角色、触发条件和规则；随后写用户流程、状态变化、异常与权限；最后给验收、范围外事项、依赖和待决。简单需求可以自然段加流程表，不必硬套章节。

**需求与设计对应**：每项设计都应回答某个问题或约束。用需求编号/验收编号建立追溯关系；没有对应问题的功能应说明来源，否则删去。验收检验用户目标和业务规则，不只检查按钮存在。

**流程与分支**：写明进入条件、动作、即时反馈、持久化状态、后续影响。并发、撤销、超时、部分成功、跨系统操作要说明资格何时生效、历史记录是否保留、如何查证、何时可恢复。

**段落推进**：问题段交代为何要改；规则段限定系统必须遵守什么；流程段说明规则如何落地；验收段把规则转成可观察结果。不要把功能列表当作需求论证。

**语言与断句**：用业务角色熟悉的术语；规则句尽量一条只表达一个条件和结果。对“有效”“完成”“成功”等易混词给出本需求中的定义。

**完整示例（合成）**：某共享实验室允许成员预约仪器。问题不是缺少预约按钮，而是两个成员可能同时取得同一时段。需求应定义预约请求的时段、成员资格和仪器状态；只有服务端确认占用成功后才生成有效预约。若请求超时，界面不能直接显示失败并鼓励重试，而应先查询预约记录；查询能力尚未确认时，将状态标为结果未知并提示联系管理员。验收至少覆盖同一时段两人并发、资格失效、超时但已写入、取消后再次预约四种情况。

**常见问题**：页面清单替代流程；把假设写成需求；权限只在角色表出现却未落实到动作；异常没有后续；验收只检查UI；把请求响应成功当业务成功。

## 2. 功能说明（FUN）

**读者任务**：用户、客服或管理员需要知道某功能适用于谁、从哪里进入、如何使用、系统会如何响应、结果如何确认。

**需要材料**：产品/版本、角色、真实入口、前置条件、用户动作、系统响应、状态定义、可见结果、权限限制、异常提示和支持渠道。按钮文案、自动行为和恢复能力必须有来源。

**组织方式**：先说明适用版本和功能用途，再按用户真实任务说明入口、前提和操作；在动作附近解释系统响应和结果；最后处理权限、异常、限制和常见疑问。面向外部用户时少写内部架构；内部功能规格可补充状态触发条件。

**动作与响应对应**：明确区分用户做了什么、系统收到什么、系统实际完成什么。输入被接受不等于后台处理完成；提交成功不等于审批通过；文件生成不等于导出已交付。

**流程与分支**：按用户的任务顺序组织；权限不足、版本差异、无数据、部分成功和请求结果未知应在相关步骤处说明。

**段落推进**：用途限定适用范围；入口段让用户到达功能；操作段让用户完成动作；反馈段帮助判断下一步；异常段解释何时停止或求助。

**语言与断句**：直接使用用户界面真实名称。没有已知入口时写明版本/部署待确认，不写“点击设置”之类猜测。

**完整示例（合成）**：在仓储系统4.3中，具备“库存调整”权限的仓库主管可从“库存—调整单”查看待处理单据。选择单据后核对SKU、库位和调整数量；提交后单据进入“待复核”，库存余额不会立即变化。复核人通过后，单据变为“已过账”，库存余额才更新。若页面显示提交超时，不要重复创建调整单；先按单据编号查询状态。系统是否提供查询入口若未在版本说明中给出，应先联系系统管理员确认，不能臆造按钮。

**常见问题**：把拟议功能写成已上线；虚构按钮；混淆提交与完成；角色权限不一致；过多实现术语；缺少结果确认。

## 3. 技术方案说明（TECH）

**读者任务**：研发、架构、运维或评审者需要理解方案如何满足约束、为什么选择它、代价是什么、故障时如何维持正确状态。

**需要材料**：业务不变量、负载/时延/一致性约束、数据模型、接口契约、部署边界、权限、依赖服务、现有技术栈、可观测指标、恢复要求和备选方案。

**组织方式**：先说明需要满足的业务不变量和现实约束；接着解释候选方案及取舍；再沿一条请求/数据流说明组件、持久化、权限和状态；最后处理故障恢复、迁移、监控与验收。不要为显得技术化而堆术语。

**设计与问题对应**：唯一性问题才需要唯一约束或幂等键；并发争用才讨论锁/原子更新；重复消息才讨论去重；跨系统状态不能原子提交时，应说明一致性窗口与补偿边界。每个技术选择都要回应一个具体约束。

**流程与分支**：区分请求已到达、写入已提交、响应已返回、下游已处理。写出超时、重复、乱序、部分成功和恢复失败时可观察的状态。没有接口契约时，列为设计前提或待确认，不声称已存在。

**段落推进**：约束引出设计要求；设计选择解释如何满足约束；数据流展示具体实现位置；异常段检验方案在失败时是否仍守住不变量；验收把约束转成测试条件。

**语言与断句**：首次出现的关键术语简要解释；保留必要的表名、接口和字段，但不将读者不需要的底层细节塞进正文。

**完整示例（合成）**：预约服务每天开放500个时段，每个时段最多一台设备。两个请求可能同时读取剩余名额，因此“先查再写”不足以防止超卖。方案比较数据库条件更新与分布式锁：当前只有单库事务边界，优先采用带剩余量条件的原子更新，并在同一事务中写入预约记录。若未来跨库拆分，再评估锁服务。接口超时后，客户端不得盲目重发；需以请求幂等标识查询原预约结果。若现有接口没有查询能力，该部分是上线阻塞项。验收验证并发请求下不超卖、重复请求不重复扣减、提交后响应丢失可查明结果。

**常见问题**：堆技术名词；未比较备选；把建议写成现有实现；没有故障状态；验收与约束无关；跨系统事务承诺过度。

## 4. 项目介绍（INTRO，非求职作品集）

**读者任务**：合作方、管理者、评审者或潜在使用者需要快速判断项目解决什么问题、目前做到了哪里、证据能支持什么、下一步需要什么决定。

**需要材料**：目标对象、问题证据、项目范围、已完成工作、方法/原型/数据、结果及其口径、验证方式、局限、当前阶段、下一步决策。个人贡献和求职适配另由求职专项处理。

**组织方式**：从具体问题和对象切入；说明项目如何回应问题；交代已完成的工作与可展示成果；解释证据的范围；最后提出当前阶段和下一步合作/资源请求。研究型项目可先交代研究问题和方法，再展示发现。

**证据边界**：原型、模拟、离线数据、少量访谈、课堂作业与生产部署分开。报告指标时给出样本、时间、口径和比较基线。没有对照或线上数据，不写业务提升。

**段落推进**：问题说明项目必要性；方法段解释实际做了什么；成果段展示可核对的产物；证据段说明能得出什么；结尾聚焦下一步。

**语言与断句**：避免宏大愿景和自我表扬。用具体名词、动作和结果替代“赋能、闭环、全面提升”。

**完整示例（合成）**：社区食堂每周需要人工汇总多家供应商的到货表，格式不一，容易造成重复录入。本项目完成了一个本地原型，可读取三种约定格式、统一商品编码并生成差异清单。当前测试使用人工制作的120行样例数据，验证了字段映射和重复行提示；尚未连接食堂采购系统，也没有测量真实节省工时。下一阶段需要食堂提供脱敏历史订单，并由采购负责人确认商品编码规则，再决定是否开展小范围试用。

**常见问题**：把原型说成上线；把模拟数据说成真实业务；成果与问题无关；指标无分母；项目介绍写成求职简历；结尾只有愿景没有下一动作。

## 5. 操作文档（HOWTO）

**读者任务**：操作者在明确环境和权限下完成一项任务，并能判断产物是否正确、失败后如何安全处理。

**需要材料**：工具与版本、操作系统/环境、账号角色、入口、前置文件、目录、依赖、实际命令或菜单、预期输出、状态查询方法、错误恢复和支持责任。关键材料缺失时标明第一处阻塞。

**组织方式**：标题用任务动词；开头交代适用版本、前提和风险；随后按真实依赖顺序给动作步骤；每个关键步骤说明预期结果或检查方法；结尾说明异常处理、清理和完成判定。

**逐步走查**：每一步检查前置条件是否成立、动作是否能从给定入口执行、产物在哪里、如何验证、失败后能否安全重试。步骤编号只给真实动作，不把“已授权”或“已部署”写成步骤。

**部分成功**：明确成功范围、失败范围、已提交与未提交对象；重跑前先查状态，避免重复写入。若无法查询提交结果，停止在安全边界并请求负责人核验。

**段落推进**：前提让读者知道是否适用；步骤改变系统/文件状态；检查步骤证明结果；异常段提供安全分支。

**语言与断句**：一条动作尽量一个主要操作；命令原样放代码块；解释参数、运行目录和预期输出。不要臆造GUI入口。

**完整示例（合成）**：环境为Ubuntu 22.04，仓库已克隆到`/srv/inventory-import`，Python 3.12已安装，依赖锁文件为`requirements.lock`。操作者具有沙箱写权限。进入仓库根目录，创建`.venv`并用该环境的Python安装锁定依赖；将输入CSV放入`data/incoming/`，运行仓库提供的`python -m importer --input ... --dry-run`。预期生成`reports/preview.csv`和`reports/rejects.csv`。先检查预览行数与输入行数是否一致，再抽查拒绝原因；dry-run不写入正式库存。正式导入命令需另有审批，未获批准前不得执行。若预览文件缺失，保留日志并停止，不自行猜测命令参数。

**常见问题**：缺版本/权限；命令没有工作目录；预期输出不明；把dry-run当正式成功；失败后盲重试；将业务审批写成技术步骤。

## 6. 项目交接（HANDOFF）

**读者任务**：接手人能找到资产、获得授权、准备环境、开始工作、核对产物、处理已知故障并完成签收。

**需要材料**：仓库/文件位置与版本、负责人、环境、依赖、凭据获取流程、权限范围、数据来源、初始化方式、运行命令、预期产物、日志/状态查询、已知问题、未决事项、下一责任人和验收人。

**组织方式**：先说明项目当前状态和接手目标；列出资产及版本；交代环境与权限获取；给出从干净环境开始的启动路径；说明输出、验证与已知故障；最后列未决事项、负责人、期限和签收条件。材料充分时写出可复现的完整路径；材料缺失时仍完成可做部分并指出第一处阻塞。

**责任与状态**：区分交付人、接手人、审批人、业务验收人。文件已复制不等于接手验收；脚本可运行不等于业务结果认可。只读、沙箱写入和生产写入权限分开。

**段落推进**：当前状态告诉接手人从哪里开始；资产和环境让其准备；启动步骤产生结果；验证方法让其判断；风险与未决事项指明后续责任。

**语言与断句**：路径、命令、版本和负责人写准确；避免“相关文件”“按需配置”等不可操作表述。敏感凭据不直接写入文档，说明授权获取位置。

**完整示例（合成）**：项目仓库为`ssh://git.example.test/ops/stock-recon.git`，交付标签`v1.6.2`，默认分支`main`。接手人为数据平台主管林工，交付人为开发负责人周工，生产审批人为运维值班经理。运行环境Ubuntu 22.04、Python 3.12；依赖文件`requirements.lock`。只读数据快照位于`/srv/recon/input/2026-10-31/`，运行输出写入`/srv/recon/output/`，接手人已获沙箱写权限，生产权限须通过运维工单申请。启动前在仓库根目录创建虚拟环境并安装锁定依赖；执行`./scripts/reconcile.sh --date 2026-10-31 --input /srv/recon/input/2026-10-31 --output /srv/recon/output/run-20261031`。预期生成`summary.csv`、`unmatched.csv`和`run.log`。接手人核对输入文件清单、输出行数及日志中的完成标记，再由业务验收人抽查未匹配记录。若输入快照缺失，数据平台主管负责提供；若脚本异常退出，保留run目录与日志，不清理后重跑。生产审批由运维值班经理负责，当前交接只包含沙箱复现。

**常见问题**：路径没有起点；解释器不一致；凭据写死；没有初始化数据；命令缺参数；结果无查证方式；责任人不清；把模拟走查当成真实运行。


## 本轮修复补充：跨系统结果、到期竞争与权限边界

### TECH / PRD：未知结果、重复请求与TTL竞争

- 将“请求超时/响应丢失”单独建模为结果未知，不直接归为失败。查询能力缺失时停止重发，明确人工核验方和上线阻塞。
- 分开处理重复业务提交、消息重复投递、回调重复通知。只有在明确唯一键和幂等范围后，才能说某类重复可安全去重。
- 对预占等有有效期的资源，说明支付、确认、释放和到期的竞争顺序。状态查询不等于原子确认；若没有确认/续期接口，明确支付成功后资源已到期的业务处置待决。
- 方案可提出新增幂等键、查询或确认接口，但必须标为拟议设计/契约要求，不得写成当前已有能力。

### HOWTO：条件变化与计数口径

- 条件变化只增加参数或退出条件时，原有文件定义、行数公式、统计范围和验收口径保持不变。
- 若公式各项定义不清、与文件分流方式存在表面冲突，原样保留公式并暂停解释性改写；把“有效行”的定义、是否计表头、预览文件是否包含拒绝行等列为明确待确认项。
- 非零退出码不自动代表无产物或数据库已写入；必须依据输入说明分别核对退出码、文件产物和副作用边界。

### HANDOFF：权限与状态的逐项核验

- 分别核实主机登录、sudo命令范围、Docker daemon/socket、镜像仓库pull认证、挂载目录读写、测试部署和生产部署权限。sudo本身不证明Docker权限。
- 分开记录镜像已推送、接手主机已拉取、容器已创建、进程已启动、健康检查通过和业务验收通过；前一状态不代表后一状态。
- 预期日志文件必须给出实际路径；若镜像只说明“会生成run.log”但未给出位置，列为开发交付缺项。
