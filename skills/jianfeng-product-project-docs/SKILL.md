# 产品与项目文档 Skill

版本：2.1.0

## 适用范围

负责六类文档：产品需求文档（PRD）、功能说明（FUN）、技术方案说明（TECH）、项目介绍（INTRO，非求职作品集）、操作文档（HOWTO）、项目交接（HANDOFF）。面向招聘的个人作品集、简历项目经历和求职陈述由求职专项负责。

体裁细则见 `references/六类体裁写作指南.md`；论文 Word/PDF 排版任务见 `references/论文文档生成与排版默认规范.md`。来源与证据边界见 `references/来源依据与适用边界.md`。

## 一、开始写作

先判断读者是谁、读完要作出什么判断或完成什么动作，再确定文档结构。收集并区分：

- 已确认事实：角色、数据、版本、日期、系统行为、接口、权限、运行环境和责任人。
- 用户问题与业务目标：问题发生在谁的工作中，造成什么影响，期望改变什么。
- 已选设计与备选方案：哪些已经决定，哪些只是建议。
- 能力状态：待讨论、拟开发、已实现、已测试、已上线分别记录；不得互相替代。
- 缺失与冲突：指出影响哪项结论或动作、第一处阻塞在哪里、需要谁提供什么。

未知不等于不存在。出现接口名称不等于接口已经部署；命令写进文档不等于运行成功；生成记录不等于业务审批；HTTP成功响应不等于支付到账；预约记录仍存在不等于当前仍有资格使用资源。

不为追求完整而编造按钮、入口、错误提示、自动保存、恢复、幂等、撤销、查询、审批或权限。可以提出拟议方案，但必须标为建议或待确认，并与现有系统行为分开。

## 二、组织全文

结构服务于读者任务，不套用统一模板。可用问题、场景、决策、流程、解释、证据或操作步骤组织，但只保留能帮助读者理解或行动的部分。简单任务不强制六层目录；复杂任务可用表格、状态图、流程图或附录。

句子之间要有实质关系：后一句接住前一句的对象或条件，补充原因、动作、结果、例外、证据或决策。段落之间要有推进，不能只靠“此外”“因此”“需要强调”制造衔接。短句要完整，不把修饰语、主语或宾语硬拆。删除不推进论证的防御性语言；但权限、边界、失败恢复和待决条件若影响决策或操作，必须保留在相关位置。

不要把所有文体统一成“事实—限制—建议”。PRD要推动需求决策；TECH解释设计选择；FUN帮助使用；INTRO说明成果与下一步；HOWTO指导安全操作；HANDOFF支持接手与签收。

## 三、业务状态与条件变化

在全文中保持同一组状态定义。明确谁触发状态变化、变化何时生效、是否可逆、由谁确认、如何观察结果。把历史记录、当前资格、外部通知、支付受理、实际到账、内容发布等不同事实分开。

主流程、异常、权限和验收必须互相对应。每个重要异常都要说明触发条件、系统/人工实际响应、当前状态、操作者下一步和恢复边界。若没有可查状态或幂等契约，不得建议盲目重试。

条件变化不是附加一段“新增要求”。必须重新检查受影响的目标、角色、数据、流程、状态、异常、权限、结果、验收、版本和责任。旧版本规则可作为历史说明保留，但不得残留在新版主流程或新版完成标准中。

**只改输入明确改变的部分。** 条件变化只新增参数、权限或一个分支时，未被改变的原始公式、计数口径、路径、角色、验收定义和状态含义必须保持原样；不得为了让全文看起来更顺而自行“修正”原公式或替换成另一种统计关系。若原口径内部存在歧义或冲突，先逐字保留已给口径，并将定义、分母、是否含表头、统计范围等列为待确认；不得用常识改写成另一条公式。

**外部请求的结果未知不是失败。** 分清请求是否发出、对方是否受理、业务状态是否最终确定。超时、连接中断或响应丢失时，若没有权威查询接口或对方明确支持的幂等键，不得盲目重试。重复回调去重不等于重复提交安全：必须分别核对回调事件标识、业务请求标识、幂等范围和重试契约。若无法查明第一次请求是否已生效，保持“结果待核”并停止可能产生重复副作用的操作，指出核验责任方。

**有时限的资源必须处理到期竞争。** 对库存预占、预约锁定、临时授权等TTL资源，普通状态查询只是某一时刻的观察，不能单独消除“查询后、确认前到期”的竞争。若业务要求付款成功后仍保证资源，必须有库存方/资源方原子确认、续期或等效契约，并定义确认与到期谁先生效。接口不存在时，将支付成功但资源已过期的处置列为业务待决和上线阻塞，不得承诺资源仍被保留。

**权限按具体操作核对。** 主机sudo、目录读写、Docker CLI/daemon或socket访问、镜像仓库认证、测试环境部署和生产集群权限是不同权限。拥有其中一项不能推导出其他项；不得从“有sudo”推断“可执行docker”，也不得自行改用`sudo docker`绕过未确认的授权。文档必须写明已确认的权限范围和仍需管理员授予/核验的动作。

## 四、成稿与编辑

先写能完成读者任务的完整正文，再编辑。编辑时按以下顺序处理：

1. 事实与边界：有无虚构、越权承诺、状态偷换、数字或版本错误。
2. 业务逻辑：问题是否引出功能/设计；角色、权限、主流程、异常和验收是否一致。
3. 可用性：读者能否理解、决策或执行；关键前提和结果查证是否充分。
4. 全文组织：段落是否推进；相邻段落是否有真实联系；是否出现跨篇通用句群或固定填充段。
5. 语言：修复病句、重复、断句和不自然术语；不为偏好性改词重写已成立内容。

材料充分时写完整文档，不得用“待补清单”回避成文。材料不足时先完成有依据的部分，再准确指出第一处阻塞、影响、需要的信息及责任方。外部业务决定未提供时，交付待决说明，不自行裁决；单个待决点不应阻塞无关部分。

## 五、A/B与验证记录

只有在组织策略确实不同且会影响读者理解时才做A/B，例如按用户任务组织与按状态/约束组织。若只是交换标题、替换同义词或复述同一正文，标为对照不足，保留原稿，不强制制造两稿。

区分四类证据：
- 结构检查：文件、字段、版本、编号是否齐全。
- 作者编辑复核：对事实、逻辑、语言和读者任务的逐篇编辑。
- 材料模拟走查：仅依据给定材料推演操作链，不代表系统已运行。
- 真实执行测试：必须有真实环境、实际操作记录和可核验输出。

冻结规范后的验收材料不得参与规则修订。失败稿保留；规则修订后用新的材料复测，不覆盖或改判首次失败。不要用实验数量、结构通过率或同一作者复核冒充独立盲审。

## 六、交付

按用户要求交付可编辑正文和必要附件。文件名、版本、目录和链接准确。将产品正文与实验评语、检查清单、内部批注分开；不得把“输入规定”“本案”“模拟走查”“测试评语”等实验说明写进面向产品读者的正文。

交付前确认：
- 文档完成了目标读者任务；
- 关键事实、权限、版本和能力状态有材料依据；
- 问题—需求/设计—流程—异常—验收可追溯；
- 操作有前提、入口、动作、预期结果和失败处理；
- 交接有起点、资产、环境、权限、运行方式、产物、查证和责任；
- 条件变化已更新所有受影响位置；
- 段落有推进，语言自然，无无意义模板填充；
- 未执行的命令和未测试的行为没有被报告为通过。
